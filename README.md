# Платёж прошёл? Докажи

Небольшой отказоустойчивый сервис для проведения платёжных операций через внешний HTTP-провайдер.

Проект выполнен в рамках вступительного задания [«Платёж прошёл? Докажи»](https://github.com/fintech-dev-lab/internship-entry-task-2).

Основная задача сервиса -- обеспечить корректное состояние операции при:

* повторных запросах `submit`;
* конкурентных запросах;
* временной недоступности провайдера;
* сетевых ошибках и потерянных HTTP-ответах;
* callback, пришедшем раньше HTTP-ответа провайдера;
* повторных и конфликтующих callback;
* перезапуске сервиса.

Ключевой инвариант:

> Для одной операции создаётся не более одного платежа у провайдера, а финальный статус операции определяется только callback-квитанцией провайдера.

# API

## Создание операции

```http
POST /operations
Content-Type: application/json
```

Пример:

```bash
curl -X POST http://localhost:8080/operations \
  -H "Content-Type: application/json" \
  -d '{
    "operationId": "operation-123",
    "amount": "1000.00",
    "currency": "RUB",
    "description": "Оплата заказа"
  }'
```

Ожидаемый результат:

```json
{
  "operationId": "operation-123",
  "amount": "1000.00",
  "currency": "RUB",
  "description": "Оплата заказа",
  "status": "CREATED",
  "providerPaymentId": null
}
```

Повторное создание той же операции возвращает:

```text
409 Conflict
```

---

## Инициация отправки

```http
POST /operations/{id}/submit
```

Пример:

```bash
curl -X POST \
  http://localhost:8080/operations/operation-123/submit
```

---

## Получение операции

```http
GET /operations/{id}
```

Пример:

```bash
curl http://localhost:8080/operations/operation-123
```

Финальный статус операции устанавливается только после получения callback-квитанции от провайдера:

```text
COMPLETED
```

или:

```text
REJECTED
```

HTTP-ответ `202 Accepted` от провайдера сам по себе не означает успешного завершения платежа.

---

## История операции

Пример:

```json

    "fromStatus": null,
    "toStatus": "CREATED",
    "message": "Operation created",
    "occurredAt": "2026-07-15T12:00:00Z"
  }
]
```

# Проверка отказоустойчивости

Сервис рассчитан на следующие сценарии.

## Повторный submit

Повторные запросы:

```bash
curl -X POST \
  http://localhost:8080/operations/operation-123/submit

curl -X POST \
  http://localhost:8080/operations/operation-123/submit
```

не должны создавать несколько намерений отправки или несколько платежей у провайдера.

---

## Конкурентный submit

Несколько запросов можно отправить одновременно:

```bash
seq 10 | xargs -n1 -P10 -I{} \
  curl -s -X POST \
  http://localhost:8080/operations/operation-123/submit
```

Ожидаемый результат:

* создаётся только одно намерение отправки;
* создаётся только один `SendJob`;
* операция не переводится в некорректное состояние;
* провайдер получает не более одного платежа благодаря `Idempotency-Key`.

---

## Повторные и конфликтующие callback

Повторная одинаковая callback-квитанция обрабатывается идемпотентно и не создаёт повторного перехода операции в то же состояние.

Конфликтующая поздняя квитанция с противоположным результатом не изменяет уже установленный финальный статус операции. Такая квитанция фиксируется в истории как проигнорированная.

# Архитектура

Сервис состоит из API, постоянного хранилища PostgreSQL и трёх фоновых обработчиков отправки платежей.

```text
                         ┌──────────────────────┐
                         │      Client/API      │
                         └──────────┬───────────┘
                                    │
                     POST /operations/{id}/submit
                                    │
                                    ▼
                         ┌──────────────────────┐
                         │      PostgreSQL      │
                         │                      │
                         │ Operation            │
                         │ SendJob              │
                         │ Event                │
                         └──────────┬───────────┘
                                    │
                              PENDING SendJob
                                    │
                                    ▼
                         ┌──────────────────────┐
                         │    PendingWorker     │
                         │                      │
                         │ PENDING → RUNNING    │
                         └──────────┬───────────┘
                                    │
                                    ▼
                         ┌──────────────────────┐
                         │    RunningWorker     │
                         │                      │
                         │ HTTP /payments       │
                         └──────────┬───────────┘
                                    │
                         ┌──────────┴──────────┐
                         │                     │
                       success               error
                         │                     │
                         ▼                     ▼
                       DONE              WAITING_RETRY
                                               │
                                               ▼
                                        RetryWorker
                                               │
                                        retry / backoff
                                               │
                                         ┌─────┴─────┐
                                         │           │
                                       success     error
                                         │           │
                                         ▼           ▼
                                       DONE    WAITING_RETRY
```

### Operation

`Operation` представляет бизнес-состояние платежной операции.

Поддерживаемые состояния:

* `CREATED` — операция создана, отправка ещё не запрошена;
* `PROCESSING` — намерение отправки надёжно сохранено, ожидается результат провайдера;
* `COMPLETED` — провайдер подтвердил успешный платёж callback-квитанцией;
* `REJECTED` — провайдер подтвердил отказ callback-квитанцией.

Финальный статус `COMPLETED` или `REJECTED` устанавливается исключительно на основании callback-квитанции.

### SendJob

`SendJob` отвечает за надёжную доставку намерения отправить платёж провайдеру.

Состояния:

* `PENDING` — отправка запланирована;
* `RUNNING` — задача взята воркером и выполняется;
* `WAITING_RETRY` — попытка завершилась ошибкой, ожидается повтор;
* `DONE` — запрос провайдеру успешно принят.

`Operation` и `SendJob` разделяют бизнес-состояние платежа и состояние доставки запроса провайдеру.

### PendingWorker

`PendingWorker` находит новые `SendJob` в состоянии `PENDING` и атомарно переводит их в `RUNNING`.

Это позволяет зафиксировать намерение отправки до выполнения внешнего HTTP-вызова.

### RunningWorker

`RunningWorker` обрабатывает `RUNNING`-задачи и выполняет HTTP-запрос к провайдеру.

При успешном ответе:

```text
RUNNING → DONE
```

При сетевой ошибке или временной ошибке провайдера:

```text
RUNNING → WAITING_RETRY
```

Полученный `providerPaymentId` сохраняется, но статус `Operation` не переводится в финальное состояние.

### RetryWorker

`RetryWorker` обрабатывает задачи `WAITING_RETRY` после наступления времени следующей попытки.

При успешной повторной отправке:

```text
WAITING_RETRY → DONE
```

При повторной ошибке задача остаётся:

```text
WAITING_RETRY
```

и планируется следующая попытка согласно retry policy.

## Надёжность и идемпотентность

Для каждой операции все запросы к провайдеру используют:

```text
Idempotency-Key = operationId
X-Correlation-ID = operationId
```

Повторные HTTP-запросы используют тот же `Idempotency-Key` и неизменное тело запроса.

Если сервис падает после фактического принятия платежа провайдером, но до сохранения HTTP-ответа, повторная отправка после восстановления использует тот же ключ идемпотентности.

Провайдер в таком случае возвращает тот же `providerPaymentId`, не создавая второй платёж.

Финальный результат операции при этом всё равно определяется только callback-квитанцией.

---

## Конкурентный submit

`Operation` используется как точка сериализации изменений конкретной операции.

Перед изменением `Operation`, `SendJob` или `Event` соответствующая строка `Operation` блокируется через `SELECT ... FOR UPDATE`.

Это гарантирует корректную обработку конкурентных запросов `submit`.

Дополнительная гарантия обеспечивается базой данных: `SendJob.operation_id` является первичным ключом, поэтому для одной операции физически не может существовать более одного `SendJob`.

---

## Callback

Callback-квитанция является единственным источником финального результата платежа.

Возможен callback до получения HTTP-ответа от провайдера.

Если `providerPaymentId` ещё не сохранён локально, он устанавливается из первой валидной callback-квитанции.

Если HTTP-ответ провайдера приходит позже, он не может вернуть операцию из финального состояния обратно в `PROCESSING`.

Повторная одинаковая квитанция не создаёт повторного перехода в то же состояние.

Поздняя конфликтующая квитанция с противоположным результатом не изменяет финальный статус и фиксируется в истории как проигнорированная.

---

## Сохранность данных

Операции, намерения отправки, `providerPaymentId` и история событий хранятся в PostgreSQL и переживают перезапуск контейнеров при сохранении Docker volume.

Незавершённые операции после запуска сервиса снова подхватываются фоновыми обработчиками.

Повторная отправка после сбоя использует исходный `operationId` как `Idempotency-Key`, поэтому восстановление не приводит к созданию второго платежа у провайдера.

---

# Ключевые инварианты

Проект поддерживает следующие инварианты:

1. `operationId` уникален.
2. Для одной операции существует не более одного `SendJob`.
3. `SendJob.operation_id` является `PRIMARY KEY`.
4. Изменения `Operation`, `SendJob` и `Event` выполняются после блокировки соответствующей строки `Operation`.
5. Конкурентные изменения одной операции сериализуются через `SELECT ... FOR UPDATE`.
6. Намерение отправки фиксируется до внешнего HTTP-вызова.
7. HTTP-вызов провайдера не выполняется внутри транзакции с блокировкой `Operation`.
8. Все повторные запросы провайдеру используют один `Idempotency-Key`, равный `operationId`.
9. `202 Accepted` от провайдера не переводит `Operation` в финальное состояние.
10. Финальный статус `COMPLETED` или `REJECTED` устанавливается только callback-квитанцией.
11. Потеря HTTP-ответа не приводит к созданию второго платежа.
12. Повторная callback-квитанция не создаёт повторный переход состояния.
13. Конфликтующий `providerPaymentId` не может незаметно заменить уже установленный идентификатор.
14. Незавершённые операции восстанавливаются после перезапуска.
